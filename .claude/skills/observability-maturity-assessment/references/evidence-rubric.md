# 証跡 → レベル判定ルーブリック

成熟度モデルの各レベル定義（`csv/observability-maturity-model.csv`）を、「リポジトリの成果物で確認できる要件」と「組織・運用の実態でしか確認できない要件」に分解したもの。`scan_repo.py` の出力（`evidence.json` / `evidence-summary.md`）を読みながら、この表に沿って暫定レベルと確信度を決める。

## 判定の原則

1. **レベルは「定義の主要要件が証跡で直接確認できる最高のレベル」**。上位レベルの成果物が 1 つあるだけ（例: 異常検知の設定が 1 本ある）では上位レベルとしない。下位レベルの要件が満たされていない場合も上位レベルとしない。
2. **シグナルの `hint_level` は目安**であって判定ではない。`hint` が L4 のシグナルがヒットしても、L2・L3 の要件に証跡がなければ L2 以下。
3. **証跡の強さ**: `path`（配置）・`config`・`code`・`deps` ＞ `docs`（文書への言及のみ）。文書のみの場合は「実装・運用されている」とは判断せず、確信度を下げる。
4. **レベル3以上は組織横断性が要件**（「組織全体で標準化」「全プロジェクトで一貫して適用」）。単一リポジトリで確認できるのは「このリポジトリが標準に従っていること」まで。レベル3以上の判定は原則 **確信度『中』以下**とし、組織横断の適用状況をヒアリング質問にする。ただし、共通モジュール・組織標準テンプレート・共有 IaC モジュール等への参照があれば、組織標準の存在を示す中程度の証跡として扱える。
5. **レベル4は「定量的に測定・制御」**。KPI の定義だけでなく、測定結果に基づく判断・調整が行われている痕跡（閾値の自動判定、レビュー記録、調整履歴）を求める。
6. **レベル5は「自動化された継続的最適化が組織文化として定着」**。AI/ML ツールの導入だけでは不足。改善提案→適用までが人手を介さず回っていることと、その運用期間・実績を要求する。リポジトリだけでレベル5と判定することは基本的にできない（確信度『低』）。
7. **判定できないときは「未評価」（`level: null`）**を選ぶ。A5（ユーザー行動）はバックエンド専用リポジトリやライブラリでは対象外になりうる。無理に L1 にしない。
8. **評価対象は「このリポジトリが属するサービス・チーム」**。モノレポや組織横断リポジトリ（platform/infra）の場合は範囲を `scope` に明記する。

## 確信度の付け方

| 確信度 | 条件 |
|---|---|
| 高 | レベル定義の主要要件すべてに `config`/`code`/`deps`/`path` の証跡があり、運用の継続性（更新履歴、複数の記録）も確認できる |
| 中 | 主要要件の過半に強い証跡があるが、一部は文書のみ、または組織横断性・運用実態が未確認 |
| 低 | 証跡が断片的、または文書のみ。主に推定 |

## A1. データ収集と可視化

| レベル | リポジトリで確認できる要件（証跡の例） | リポジトリで確認できない要件（ヒアリング） |
|---|---|---|
| L1 属人的 | 監視・ログ収集の設定が無い／断片的。構造化ログなし。ダッシュボード定義なし | 実際に誰かが手作業で見ているか |
| L2 プロセス確立 | メトリクス公開（`metrics-endpoint`）、構造化ログ（`structured-logging`）、エージェント／収集設定が存在。収集手順書やダッシュボード定義がある | 担当と実施頻度が決まっているか、データ品質の点検をしているか |
| L3 組織標準化 | 全層（インフラ・アプリ・NW・DB）の収集設定、OTel/統合基盤（`otel-sdk` `vendor-agent-config`）、ダッシュボードのコード管理と共通テンプレート（`dashboards-as-code`）、分散トレーシング | 標準が組織全体で文書化・適用されているか。共通テンプレートが他チームでも使われているか |
| L4 定量管理 | 収集データ自体の品質監視（`data-quality-monitoring`: 欠損検知・エージェント死活）、検知精度・遅延の KPI 文書（`monitoring-kpi-docs`）、動的ベースライン | KPI が定期レビューされ、閾値調整や設定変更の判断に使われているか。誤検知率・見逃し率の実測値 |
| L5 継続的最適化 | 予測分析と設定の自動最適化（`aiops-forecast`）が本番構成に組み込まれている | 改善提案→導入が自動で回っている実績。人的介入の頻度 |

## A2. システムの信頼性管理

| レベル | リポジトリで確認できる要件 | 確認できない要件 |
|---|---|---|
| L1 | ヘルスチェックや対応手順の記述なし。インシデントの記録なし | 対応履歴が残っているか |
| L2 | ヘルスチェック（`health-probes`）、インシデント対応手順・エスカレーション文書（`incident-process-docs`）、稼働率・応答時間など基本指標の定義 | 手順が実際に使われているか。指標を定期的に見直しているか |
| L3 | SLI/SLO 定義（`slo-definitions`）、ランブック／プレイブック（`runbooks`）、ポストモーテムのテンプレートと実例（`postmortems`）、リスク一覧（`risk-register`） | 組織標準プロセスとして全チームに適用されているか。SRE 担当が明確か。ポストモーテムの実施率 |
| L4 | CI/CD への信頼性チェック（`reliability-gates-ci`）、カオスエンジニアリング（`chaos-engineering`）、障害時データ自動収集、予兆検知ルール | MTTR/MTBF 等の統計的評価と、再発防止策の効果測定が行われているか |
| L5 | 自動復旧・自動ロールバック（`auto-remediation-reliability`）が本番で有効 | 予兆検知→対応の全自動化の実績、ナレッジ自動蓄積 |

## A3. 開発・運用プロセスの整備と最適化

| レベル | リポジトリで確認できる要件 | 確認できない要件 |
|---|---|---|
| L1 | CI なし、リンタなし、テストほぼなし、レビュー体制の記述なし | — |
| L2 | CI（`ci-pipeline`）、静的解析（`static-analysis`）、コードレビュー体制（`code-review-process`）、自動テスト（`automated-tests`）。※テストが CI から呼ばれていなければ L2 止まり | レビューが一貫して実施されているか。リリースのスケジュール管理 |
| L3 | CD／ステージング環境（`cd-pipeline`）、IaC（`iac`）、CI で単体・統合テストが自動実行、リリース自動化（`release-automation`）、依存更新自動化（`dependency-automation`） | 影響評価がデプロイ前に実施されているか。標準テンプレートが他プロジェクトでも使われているか |
| L4 | カバレッジ閾値・品質ゲート（`coverage-thresholds`）、DORA 等のデリバリー KPI（`dora-metrics`）、プログレッシブデリバリーと自動ロールバック（`progressive-delivery`） | KPI の定期レビューと改善への反映。リリース後影響の即時分析体制 |
| L5 | AI によるコード解析・影響分析・リリース可否判断（`ai-code-review`）が CI/CD に組み込まれている | 自動判断の対象範囲と実績。人の関与の度合い |

## A4. アラート最適化と障害対応

| レベル | リポジトリで確認できる要件 | 確認できない要件 |
|---|---|---|
| L1 | 固定しきい値のアラートのみ（`alert-rules` はあるが severity・ルーティング・runbook なし） | 誤検知・見逃しの実態。手動対応の負荷 |
| L2 | 重要度分類（`alert-severity`）、通知ルーティング／オンコール連携（`alert-routing`）、しきい値調整の履歴 | 棚卸しが行われたか。ノイズ削減の効果 |
| L3 | 動的しきい値／異常検知（`dynamic-thresholds`）、アラートと初動手順の紐づけ（`alert-runbook-links`）、アラートレビューの記録（`alert-review-process`） | アラートレビュー会の定期開催。初動マニュアルが実際に使われているか |
| L4 | 深刻度別の対応フロー・即時エスカレーション（`sev-escalation-flow`）、AI／相関による優先度付け（`ai-alert-prioritization`） | 自動チューニングの実績。SEV-1 シミュレーションの実施 |
| L5 | アラート起点の自動対処（`auto-remediation-alerts`）が本番で有効 | オペレーター介入なしで完結している割合 |

## A5. ユーザー行動の理解と最適化

対象外になりうる軸。バックエンド専用・ライブラリ・インフラリポジトリでは `level: null`（未評価）とし、理由を `rationale` に書く。

| レベル | リポジトリで確認できる要件 | 確認できない要件 |
|---|---|---|
| L1 | 解析 SDK・イベント送信なし | 改善施策が勘に依存しているか |
| L2 | 解析 SDK（`web-analytics-sdk`）、RUM（`rum`）の導入 | PV/UU 等を見て意思決定しているか |
| L3 | イベント設計・トラッキングプラン（`event-tracking-plan`）、プロダクト KPI の定義（`product-kpi-docs`）、ユーザーフロー／ファネルの可視化定義 | KPI に基づく継続的な機能改善の実績 |
| L4 | 実験基盤（`experimentation`）、パーソナライズ／行動予測モデル（`personalization-ml`）が本番コードに組み込まれている | リアルタイム最適化が実運用されているか |
| L5 | 分析→施策適用の自動化（`automated-ux-optimization`） | 自動最適化の実績と効果検証 |

## A6. 継続的な改善と最適化

| レベル | リポジトリで確認できる要件 | 確認できない要件 |
|---|---|---|
| L1 | ふりかえり・改善の記録なし | — |
| L2 | ふりかえりの記録（`retrospectives`）、課題の共有 | 定期的に実施されているか。アクションに落ちているか |
| L3 | 改善アクションの追跡（`action-item-tracking`）、ADR（`adr`）、開発・運用指標の可視化（`engineering-metrics`）、ナレッジベース（`knowledge-base`） | 改善プロセスが明文化され、組織として整備されているか |
| L4 | 改善サイクルの計測・制御（`improvement-governance`）、定量・定性の課題分析記録 | 成果の定量評価と最適化が標準業務になっているか |
| L5 | 改善ポイントの自動特定・提案・実行（`automated-improvement-detection`） | 自律的改善の実績 |

## よくある誤判定

- **ツール名の言及＝導入** と見なす。README の「将来 Datadog を導入予定」は証跡にならない。
- **デモ・サンプル・テスト用の設定** を本番運用の証跡にする（`examples/`, `samples/`, `test/` 配下の設定は除外または弱い証跡）。
- **モデルの語彙と一致した文書** をヒットと見なす（本モデル自体を置いているリポジトリ、SRE 教材など）。
- **自己申告ドキュメント**（「我々はレベル3です」）をそのまま採用する。
- **モノレポの一部** だけを見て全体を評価する。`scope` に対象範囲を書く。
- **shallow clone** では更新頻度・継続性（コミット履歴）が見えない。継続性を要する判断（運用の定着）は確信度を下げる。
