# A2. システムの信頼性管理

**能力の定義**: システムの可用性や性能を維持・向上するために、障害対応・復旧プロセスを整備し、観測指標に基づく信頼性評価とリスク要因の改善を継続的に実施する能力。

<a id="level-1"></a>
## レベル1: 属人的

**説明**

障害対応は個人の経験と判断に依存しており、対応手順や評価の仕組みは明文化されていない。可用性や性能に関する観測指標も定義されておらず、チームとしての体系的な改善活動は実施されていない。

**具体例**

監視ツールは導入されているが、アラート対応は属人的である。対応履歴や影響範囲の記録が残らず、同様の問題が繰り返されている。システムの可用性や性能に関する目標や基準が未整備であり、観測指標の定義や評価の仕組みも存在していない。システムリスク要因の管理プロセスも確立されていない。

<a id="transition-1-2"></a>
### レベル1→レベル2 に進むには

**改善アクション（必須）**: 障害対応の属人化を防ぐため、インシデント対応フローや手順書（例：一次対応、エスカレーション、復旧完了の流れ）を明文化します。また、通知ルールやログ記録方針など、初動対応に必要な基本ルールを整備します。可用性や性能に関する基本的な観測指標（システム稼働率、応答時間など）を定義し、測定を開始します。

**活用アクション（推奨）**: 定義した対応手順をチーム内で共有し、障害対応訓練（例：障害シミュレーション、ロールプレイングなど）を実施します。さらに、可用性・応答時間などの基本的な観測指標を定め、週次などで可視化・確認する体制を整備します。インシデントの記録やエスカレーション手順を文書化し、組織的な初動対応体制の構築を進めます。

> **注意点メモ**: フローの作り込みよりも、まずは「誰でも迷わず対応できる最低限の仕組み」に重点を置きましょう。訓練やレビューを継続することで、手順の定着と改善が進みます。観測指標は重要なものから段階的に追加し、組織的な体制構築への橋渡しを意識してください。

<a id="level-2"></a>
## レベル2: プロセス確立

**説明**

監視ツールや対応手順書を活用した基本的なインシデント管理プロセスが整備されており、プロジェクトレベルで計画的な対応が行われている。稼働状況や応答時間など、監視指標や性能指標をもとに改善を試みる仕組みも導入されている。

**具体例**

インシデントの記録やエスカレーション手順を文書化し、チーム内で一定のルールに従って対応している。可用性や性能に関する基本的な観測指標（システム稼働率、応答時間など）を明示し、定期的に見直している。

<a id="transition-2-3"></a>
### レベル2→レベル3 に進むには

**改善アクション（必須）**: インシデントの検知・記録・分析・再発防止を一貫して扱う対応プロセスを標準化し、各チームで運用可能なテンプレート（例：リアルタイムインシデントレポート、ポストモーテム）を整備します。可用性やエラーレートなどの信頼性指標に基準値を設定し、定期レビューを実施します。特にMTTR、MTBF、可用性などの信頼性指標の測定・共有体制を整備します。システムリスク要因の一覧と評価基準を整備し、リスク度に応じた優先順位付けを行います。

**活用アクション（推奨）**: 各チームに信頼性管理の責任者（例：SRE担当者、運用リーダーなど）を明確にし、共通のプレイブックに基づいた対応体制を整備します。これらの信頼性KPI（MTTR、MTBFなど）を定期的にレビューし、システムリスク要因の優先順位付けと改善計画の策定に活用します。組織横断での標準プロセス適用により、全プロジェクトで一貫した信頼性管理を実現します。

> **注意点メモ**: 記録作業だけで満足せず、振り返り結果がプロセス改善やリスク対策に活かされているかを定期的に確認しましょう。組織標準プロセスの導入は段階的に行い、現場の負担を考慮しながら進めることが重要です。KPIは単なる数値管理ではなく、改善の起点として活用し、実際の改善アクションにつなげることを重視してください。

<a id="level-3"></a>
## レベル3: 組織標準化

**説明**

組織全体で標準化されたインシデント対応プロセスおよびシステムリスク要因管理プロセスが整備され、全プロジェクトで一貫して適用されている。信頼性の指標と達成基準が組織共通で整備され、継続的に評価されている。

**具体例**

各チームのSRE担当者が、共通の組織標準プロセス（例：リアルタイムインシデントレポート、ポストモーテム）に基づき、インシデントの検知・対応・復旧・振り返りを実施している。可用性やエラーレートなどの観測指標に基準値を設定し、定期的にレビューしている。プレイブックによる対応標準化や、システムリスク要因の優先順位付け・改善計画も整備している。

<a id="transition-3-4"></a>
### レベル3→レベル4 に進むには

**改善アクション（必須）**: 稼働率・障害件数・復旧時間などの信頼性指標を統計的にモニタリングし、定量的な改善評価を可能にする仕組みを整えます。インシデントごとの再発防止策や対応時間の改善効果も定期的に分析します。障害発生時に収集する情報（例：メトリクス、ログ、トレース情報）を標準化し、障害発生直後に自動で必要なデータが集められる仕組みを構築します。

**活用アクション（推奨）**: 信頼性評価の結果をもとに、予兆検知のルールを更新し、重大障害の未然防止に向けた改善策を導入します。CI/CDパイプラインにも信頼性チェック（例：品質ゲート、デプロイ前の自動品質検証）を組み込み、品質確保につなげます。収集された稼働データをもとに、再発防止策や対応遅延の改善効果などを統計的に評価し、障害対応力を継続的に向上させます。

> **注意点メモ**: 可視化・分析だけで終わらず、信頼性指標に基づいたアクション（予防・再発防止）に確実につなげてください。統計的評価には十分なデータ蓄積が必要なため、段階的にKPIを設定し改善していくことが重要です。予兆検知精度は運用データに応じて継続的に調整し、過検知・見逃しの両面から最適化しましょう。

<a id="level-4"></a>
## レベル4: 定量管理

**説明**

観測された信頼性指標（例：稼働率、障害件数、対応時間など）をモニタリングし、対応プロセスやリスク要因削減の成果を統計的に評価している。予兆検知や事後レビューと連携して、改善を管理している。

**具体例**

収集された稼働データをもとに、再発防止策や対応遅延の改善効果などを評価している。予兆検知の仕組みにより、障害の兆候を早期に特定できるようにしており、CI/CDパイプラインにも信頼性のチェックを組み込んでいる。

<a id="transition-4-5"></a>
### レベル4→レベル5 に進むには

**改善アクション（必須）**: ログやメトリクスの高度な分析により、障害予兆の検出と影響評価を自動化します。インシデントの種類ごとに復旧処理を自動実行する機能を構築し、サービス影響を最小化します。復旧履歴やナレッジの自動蓄積・共有機能も整備し、組織全体で自律的な信頼性向上サイクルが継続的に実現される仕組みを構築します。

**活用アクション（推奨）**: 自動化された障害予兆検知、復旧支援、改善提案により、自律的な運用改善を実現します。機械学習による予測分析とAI技術を活用し、復旧履歴やナレッジの自動蓄積・共有を行います。パフォーマンス異常や障害予兆の分析・対応が全自動化され、サービス影響を最小限に抑えながら継続的な改善を実現します。

> **注意点メモ**: 高度な分析技術（機械学習・AI等）導入時は、判断根拠の可視化や人的レビューの併用が欠かせません。段階導入と継続改善によって、信頼性の自動化水準を高めましょう。導入初期は過剰な期待を持たず、継続的な改善が組織文化として定着することを重視してください。自律的に改善が回る文化の構築が最終目標です。

<a id="level-5"></a>
## レベル5: 継続的最適化

**説明**

観測データのAI・機械学習による高度な分析が自律的に実行されており、障害予兆の検知から対応まで全自動化されている。継続的な改善が組織文化として定着し、人的介入を最小限に抑えた予防的な信頼性向上が実現されている。

**具体例**

AIがログ・メトリクスを解析して障害予兆を検知しており、インシデント種別に応じた復旧手順を自動実行している。パフォーマンス異常や障害予兆の分析・対応を全自動化し、対応記録やナレッジも自動的に蓄積・共有している。サービス影響を抑えながら、継続的な改善もAIにより自律的に実現している。
