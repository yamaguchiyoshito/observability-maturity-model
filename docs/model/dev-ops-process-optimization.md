# A3. 開発・運用プロセスの整備と最適化

**能力の定義**: コードの品質を維持したまま、予測可能で安定したデリバリーを実現する能力。

## レベル一覧

| レベル | 名称 | 説明 |
|---|---|---|
| [レベル1](#level-1) | 属人的 | コード品質の基準やレビュー体制が整備されておらず、開発およびリリースは属人的かつ場当たり的に実施されている。 |
| [レベル2](#level-2) | プロセス確立 | 静的解析やコードレビューを導入し、一部の品質管理が実施されている。リリースも一定のスケジュールで管理されているが、運用にはばらつきがある。 |
| [レベル3](#level-3) | 組織標準化 | CI/CDパイプラインが整備され、自動テストやステージング環境を活用して品質と本番環境の安定性を確保している。 |
| [レベル4](#level-4) | 定量管理 | コード品質やリリースの結果をKPIとして定量的に測定し、影響範囲の可視化とフィードバックループを通じて継続的な改善を実施している。 |
| [レベル5](#level-5) | 継続的最適化 | AIによるコード解析と変更影響分析により、リスクやバグを自動で検出し、レビューからデプロイまでのプロセスを完全自動化している。 |

## レベル1: 属人的

<div class="omm-block omm-desc"><p class="omm-block-title">説明<span>このレベルにある組織・チームの状態</span></p><p>コード品質の基準やレビュー体制が整備されておらず、開発およびリリースは属人的かつ場当たり的に実施されている。</p></div>

<div class="omm-block omm-example"><p class="omm-block-title">具体例<span>状態を具体化した例。自組織の実態と照らし合わせる</span></p><p>開発者ごとにコードの書き方が異なっており、統一されたコーディング規約や品質基準が存在していない。テスト工程はほとんど実施されておらず、バグが頻発している。リリースは計画性に欠けており、突発的に実行されることが多い。</p></div>

<a id="transition-1-2"></a>
### レベル1→レベル2 に進むには

<div class="omm-block omm-required"><p class="omm-block-title">改善アクション<span>必須 — 次のレベルに進むための最小限の実施事項</span></p><p>リリースや運用を安定的に行うために、担当者ごとの役割分担や意思決定フローを整理し、最低限のプロセス構造（例：手順概要、責任者の明示）を図やリストで可視化します。あわせて、静的解析ツールを導入して、コード品質の基本的な問題検出を自動化し、簡易なコードレビューを実施できる体制を整備します。</p></div>

<div class="omm-block omm-recommended"><p class="omm-block-title">活用アクション<span>推奨 — 改善アクションの実効性を高め、次のレベルでの成功確率を上げる施策</span></p><p>整理したプロセス構造に基づき、特にリリース・運用に関わる業務において、確認すべき観点を明文化したチェック項目リスト（例：コードレビュー観点、テスト完了条件、デプロイ確認項目など）を整備します。これらのチェック項目はテンプレート化し、チーム全体に共有したうえで、定期的な見直し・改善を行います。</p></div>

<div class="omm-block omm-note"><p class="omm-block-title">注意点メモ<span>実施時に注意すべき点、誤解しやすい点</span></p><p>すべてのフェーズを一度に整備するのではなく、まずは「リリース」「本番反映」「運用引き継ぎ」など、サービス品質に直接影響を与える工程から着手するのが効果的です。整備したルールは実運用で活用されているかを常に確認し、形骸化しないよう改善を継続してください。</p></div>

## レベル2: プロセス確立

<div class="omm-block omm-desc"><p class="omm-block-title">説明<span>このレベルにある組織・チームの状態</span></p><p>静的解析やコードレビューを導入し、一部の品質管理が実施されている。リリースも一定のスケジュールで管理されているが、運用にはばらつきがある。</p></div>

<div class="omm-block omm-example"><p class="omm-block-title">具体例<span>状態を具体化した例。自組織の実態と照らし合わせる</span></p><p>静的解析ツールを活用して最低限の品質チェックを自動化している。コードレビューを実施してバグの抑制に取り組んでいるが、レビュープロセスには一貫性がない。リリースは定期的に行っているものの、品質保証体制が不十分でスケジュールの遅延が発生している。</p></div>

<a id="transition-2-3"></a>
### レベル2→レベル3 に進むには

<div class="omm-block omm-required"><p class="omm-block-title">改善アクション<span>必須 — 次のレベルに進むための最小限の実施事項</span></p><p>プロセスごとに標準的なテンプレートや手順書（例：設計書テンプレート、リリース手順書など）を整備し、誰が作業しても一定品質が保たれる基盤を作ります。また、手順の自動化と一貫性を確保するため、CI/CDパイプラインの整備または改善にも取り組みます。特に、リリースに関わる作業手順の標準化と自動化を優先します。</p></div>

<div class="omm-block omm-recommended"><p class="omm-block-title">活用アクション<span>推奨 — 改善アクションの実効性を高め、次のレベルでの成功確率を上げる施策</span></p><p>標準化された手順に基づいて作業できているかを定期的に確認するため、プロセスレビュー（例：リリース後振り返り、運用作業監査など）を実施し、必要に応じてプロセス自体の改善サイクルを回します。</p></div>

<div class="omm-block omm-note"><p class="omm-block-title">注意点メモ<span>実施時に注意すべき点、誤解しやすい点</span></p><p>単にドキュメントを整備するだけで満足せず、「現場で使われているか」「運用に活きているか」を重視してプロセスを育てていく意識が重要です。標準化と改善はセットで考えましょう。</p></div>

## レベル3: 組織標準化

<div class="omm-block omm-desc"><p class="omm-block-title">説明<span>このレベルにある組織・チームの状態</span></p><p>CI/CDパイプラインが整備され、自動テストやステージング環境を活用して品質と本番環境の安定性を確保している。</p></div>

<div class="omm-block omm-example"><p class="omm-block-title">具体例<span>状態を具体化した例。自組織の実態と照らし合わせる</span></p><p>コードの変更がマージされると、単体テスト・統合テスト・リグレッションテストが自動で実行される仕組みを整備している。本番環境へのデプロイ前には影響評価も実施しており、リリースに伴う障害リスクを抑制している。</p></div>

<a id="transition-3-4"></a>
### レベル3→レベル4 に進むには

<div class="omm-block omm-required"><p class="omm-block-title">改善アクション<span>必須 — 次のレベルに進むための最小限の実施事項</span></p><p>各プロセスフェーズでの成果物（例：設計書、テスト結果、リリースチェックリストなど）に対して、品質チェックポイント（例：レビュー項目、検証項目）を明確化し、ドキュメントや作業結果を客観的に評価できる基準を整備します。</p></div>

<div class="omm-block omm-recommended"><p class="omm-block-title">活用アクション<span>推奨 — 改善アクションの実効性を高め、次のレベルでの成功確率を上げる施策</span></p><p>品質基準に基づくレビューや検証プロセスを定着させ、開発・運用作業の質を継続的にモニタリングします。レビュー結果や検証結果に基づいて、必要に応じてプロセス改善策を定期的に立案・実施します。</p></div>

<div class="omm-block omm-note"><p class="omm-block-title">注意点メモ<span>実施時に注意すべき点、誤解しやすい点</span></p><p>チェックリストやレビュー項目は形骸化しやすいため、実際に価値を生んでいるかを常に意識し、現場のフィードバックを取り入れながら柔軟に見直していくことが大切です。</p></div>

## レベル4: 定量管理

<div class="omm-block omm-desc"><p class="omm-block-title">説明<span>このレベルにある組織・チームの状態</span></p><p>コード品質やリリースの結果をKPIとして定量的に測定し、影響範囲の可視化とフィードバックループを通じて継続的な改善を実施している。</p></div>

### レベル4→レベル5 に進むには

<div class="omm-block omm-required"><p class="omm-block-title">改善アクション<span>必須 — 次のレベルに進むための最小限の実施事項</span></p><p>開発・運用プロセス全体に対して、継続的な改善活動（例：振り返りミーティング、KPT方式など）を正式な運用サイクルに組み込みます。さらに、AIによるコード解析や変更影響分析の導入を検討し、レビューからデプロイまでのプロセス自動化を段階的に推進します。</p></div>

<div class="omm-block omm-note"><p class="omm-block-title">注意点メモ<span>実施時に注意すべき点、誤解しやすい点</span></p><p>単発的な振り返りで終わらせず、継続的な学びと改善のサイクルを回すことが重要です。プロセス改善を現場任せにせず、組織的に支援・評価する仕組みを作ると定着が進みます。</p></div>
